# Pitlane research findings

*Research snapshot: 2026-10-01. Focus: an original, read-only Android OBD-II MVP; this is not a certification or legal opinion.*

## 1. Android Bluetooth requirements

- For apps targeting Android 12 / API 31+, request `BLUETOOTH_SCAN` at runtime when discovering adapters and `BLUETOOTH_CONNECT` when communicating with paired devices. Declare `BLUETOOTH_ADVERTISE` only if Pitlane itself advertises. Keep legacy `BLUETOOTH` / `BLUETOOTH_ADMIN` declarations capped at `maxSdkVersion="30"`. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
- If scan results are not used to infer location, Android permits asserting `neverForLocation` on `BLUETOOTH_SCAN`; Android warns this can filter some BLE beacons. For older Android releases, Bluetooth scanning may require location permission; follow the Android version-specific permission matrix rather than requesting location by default. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
- Bluetooth Classic adapters commonly expose a serial/RFCOMM stream: Android's documented client flow obtains a `BluetoothSocket` using a service UUID, connects off the UI thread, then transfers data through the socket. BLE is different: Android acts as a central, scans for a peripheral, connects to its GATT server, discovers services/characteristics, and exchanges data through GATT. Do not assume a BLE dongle uses the same protocol or UUIDs as Classic SPP. [Classic Bluetooth connection guide](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices) · [BLE overview](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview)
- A paired-devices-only first release can avoid active discovery and `BLUETOOTH_SCAN`; Android's Companion Device Manager is another pairing path on API 26+, and its pairing UI does not require location permission. [Bluetooth permissions / Companion Device Manager](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)

## 2. OBD-II / SAE J1979 facts and limits

- SAE describes J1979 / ISO 15031-5 as emissions-related diagnostic communication between vehicle OBD systems and test equipment. SAE's listing says J1979-DA contains standardized data definitions, including PIDs, monitor IDs, test IDs, units/scaling, and information types; J1979 also spans multiple protocol layers and transport families, not just PID names. [SAE J1979 current catalog preview](https://saemobilus.sae.org/standards/j1979_202505-e-e-diagnostic-test-modes) · [SAE J1979-DA catalog](https://saemobilus.sae.org/standards/j1979da_202305-j1979-da-digital-annex-e-e-diagnostic-test-modes)
- A concrete government-defined inspection flow requests Mode `$01`, PID `$01` for supported/readiness-monitor status; when the MIL status indicates it is commanded on, the federal procedure requests Mode `$03` for stored DTCs. This is a useful honest initial scope: generic emissions data/readiness plus stored emissions DTCs, where supported—not whole-vehicle diagnostics. [40 CFR §85.2222](https://www.ecfr.gov/current/title-40/part-85/section-85.2222) · [40 CFR §85.2231](https://www.ecfr.gov/current/title-40/part-85/section-85.2231)
- EPA characterizes OBD as monitoring emission-control/emission-related systems and components; readiness indicates whether relevant onboard tests have completed, not a pass/fail diagnosis by itself. Federal inspection provisions explicitly distinguish supported monitors and “test complete / test not complete.” [EPA OBD regulations Q&A](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P100LW9G.TXT) · [40 CFR §85.2231](https://www.ecfr.gov/current/title-40/part-85/section-85.2231)
- Full SAE J1979 and its Digital Annex are not reproduced in the public catalog preview. The preview establishes scope, not full normative compliance rules or an exhaustive current PID table. SAE's IP policy says standards content is excluded from its general STM reuse guidelines and directs standards reuse requests to SAE. Obtain licensed standards/data or limit Pitlane to independently implemented, explicitly sourced facts; do not copy full SAE tables/text from unofficial mirrors. [SAE J1979 catalog](https://saemobilus.sae.org/standards/j1979_202505-e-e-diagnostic-test-modes) · [SAE intellectual-property policy](https://legacy.sae.org/about/legal-policies/intellectual-property)
- Supporting a few PIDs, modes, or DTCs is not proof of SAE J1979 conformance. A credible conformance claim would need the applicable licensed edition/annex, required services, encoding and error behavior, supported protocol layers, and vehicle/adapter test evidence. SAE's own scope makes clear that J1979 includes more than data-item names. [SAE J1979 catalog](https://saemobilus.sae.org/standards/j1979_202505-e-e-diagnostic-test-modes)

## 4. Safety, privacy, and a defensible MVP

- Keep the initial product read-only: polling generic data, reading readiness and codes. Do not include Mode `$04` erase, actuator tests, coding, or write operations in the MVP. Erasing codes can also invalidate readiness until monitors rerun; federal rules explicitly treat incomplete monitors as incomplete, not automatically as an emissions fault. [EPA readiness analysis](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P1002KNA.TXT) · [40 CFR §85.2222](https://www.ecfr.gov/current/title-40/part-85/section-85.2222)
- Label data as generic, emissions-focused, adapter/vehicle-dependent, and non-authoritative for roadworthiness. Do not claim all modules (ABS/airbag/transmission), proprietary manufacturer PIDs, inspection pass/fail, diagnosis certainty, or SAE compliance from a successful connection or a short PID list. [EPA OBD scope](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P100LW9G.TXT) · [SAE J1979 scope](https://saemobilus.sae.org/standards/j1979_202505-e-e-diagnostic-test-modes)
- Treat values as telemetry, not a safety-critical instrument: show unsupported/stale/error states, units, timestamps and source; advise diagnosis by a qualified technician and keep attention on driving. Avoid UI interaction while moving. These are product-safety recommendations, not claims that a phone/dongle is certified vehicle instrumentation.
- Minimize permissions and data collection. A VIN, time-stamped telemetry, and optional GPS can identify a vehicle or reveal trips; keep logs local by default, explain retention/export, request location only for an explicit feature, and do not upload by default. Android warns that BLE-paired data can be accessible to other apps on the device, so do not treat pairing alone as app-layer data protection. [Android BLE privacy warning](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview) · [kotlin-obd-api supported data](https://github.com/eltonvs/kotlin-obd-api/blob/master/README.md)
- A supportable MVP promise: connect to a declared adapter class/transport (for example, paired Classic SPP first), detect what generic emissions services/PIDs respond, display a small tested read-only subset and readiness/DTC status, and clearly report “unsupported,” “not ready,” or connection/parse errors. Add BLE only against documented adapter profiles and real-device tests; do not promise that every ELM327-labeled clone behaves alike. [Android Classic connection guide](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices) · [government monitor support requirements](https://www.ecfr.gov/current/title-40/part-85/section-85.2231)
